# CacheSim — 对象级缓存模拟框架

缓存模拟器，通过回放请求 trace 来模拟多种缓存驱逐策略，并以此框架为基础实验新算法。

## ALL Usage
#### 查看已注册的算法

```bash
python -m cache_sim --list-algorithms
```

### 模拟运行

```bash
python -m cache_sim [options]            # 单次模拟
```

| 参数 | 短选项 | 类型 | 取值 / 范围 | 默认值 | 说明 |
|------|--------|------|-------------|--------|------|
| `--config` | `-c` | str | 文件路径（YAML/JSON） | 无 | 批量实验配置文件路径，指定后按配置运行 |
| `--algorithm` | `-a` | str | `lru` / `lfu` / `fifo` / `random` / `randomized_marking` / `belady` / `bit_model_online` / `local_ratio_caching` | 无（必填） | 驱逐算法注册名（见 [算法说明](#算法说明)） |
| `--dataset` | `-d` | str | 文件路径 / 数据集名（`twitter29` / `twitter45` / `wiki2018`）/ `synthetic` | 无（必填） | 数据集来源；`synthetic` 表示使用合成数据集 |
| `--capacity` | — | int | 正整数（字节） | 无（必填） | 对象级缓存总容量；≤0 会抛 `ValueError` |
| `--cost-model` | — | str | `bit` / `fault` / `general` | `bit` | 成本模型：`bit`=按字节（cost=size）、`fault`=每次未命中代价为 1、`general`=预留（cost=size） |
| `--output` | `-o` | str | 文件路径（`.json` 或 `.csv`） | 无 | 报告输出路径，按后缀决定输出格式 |
| `--seed` | — | int | 任意整数 | 无 | 随机种子，用于复现（合成 trace 与随机算法） |
| `--competitive` | — | flag | — | 开启 | 运行 Belady 基线并计算竞争比；用 --no-competitive 关闭 |
| `--no-integrity-check` | — | flag | — | 关闭 | 跳过启动时对文件 trace 的完整性检查 |
| `--num-pages` | — | int | 正整数 | 100 | 合成数据集对象数（仅 `--dataset synthetic` 生效）；≤0 会抛 `ValueError` |
| `--length` | — | int | 非负整数 | 1000 | 合成数据集请求序列长度；<0 会抛 `ValueError`，0 返回空 trace |
| `--size-range` | — | int×2 | `[min, max]`，min ≤ max | `[1, 1000]` | 合成对象大小范围（字节），用于 `randint` 采样 |
| `--list-algorithms` | — | flag | — | 关闭 | 列出所有已注册算法并退出 |

#### 单次模拟

```bash
# 使用文件 trace 运行 LRU 算法
python -m cache_sim --algorithm lru --dataset traces/twitter29_test10.csv --capacity 10000

# 使用内置数据集名
python -m cache_sim --algorithm lru --dataset wiki2018 --capacity 10000

# 使用合成数据集
python -m cache_sim --algorithm lru --dataset synthetic --capacity 5000 --num-pages 200 --length 5000 --seed 42

# 计算竞争比 (与 Belady 最优对比)
python -m cache_sim --algorithm lru --dataset traces/twitter29_test10.csv --capacity 10000 --competitive

# 输出到 JSON 文件
python -m cache_sim --algorithm lru --dataset traces/twitter29_test10.csv --capacity 10000 --output results/lru_result.json
```

创建配置文件 `experiment.json`:

```json
{
  "algorithms": [

    {"name": "lfu"}
  ],
  "datasets": [
    {
      "name": "twitter29_test10",
```


- `results/experiment.csv` — 表格数据 (便于导入 Excel/Pandas)

### 生成trace

```bash
python -m cache_sim gen-trace [options] -o <output>
```

生成 basic_trace（Pareto 流行度 + Bounded-Pareto 对象大小）。

| 参数 | 短选项 | 类型 | 取值 / 范围 | 默认值 | 说明 |
|------|--------|------|-------------|--------|------|
| `--num-objects` | — | int | 正整数 | 1000 | 不同对象数量 `no_objs` |
| `--popular-requests` | — | int | 正整数 | 10000 | 重复计数 / 时间上界 `reps`；最热门对象（i=0，速率 1）约产生此次数请求，总请求数为其 H_{no_objs,0.9} 倍 |
| `--pareto-shape` | — | float | > 0 | 1.8 | Bounded-Pareto 大小形状参数 α（越大对象越偏小） |
| `--min-size` | — | int | ≥ 1 | 1 | 对象大小下界  |
| `--max-size` | — | int | ≥ min-size | 10000 | 对象大小上界  |
| `--output` | `-o` | str | 文件路径 | —（必填） | 输出 trace 文件路径 |
| `--seed` | — | int | 任意整数 | 无 | 随机种子 |


|------|------|-------------|--------|------|
| `path`（位置参数） | str | 文件路径 | —（必填） | 待检查的 trace 文件路径 |
| `--max-lines` | int | 非负整数 | 0 | 最多检查的行数；`0` 表示全量检查 |

## Trace 数据格式

 trace 数据集需组织为空格分隔的格式，每行一条请求格式如下:

```
time id size [extra...]
```

| 列 | 类型 | 说明 |
|----|------|------|
| time | long long int | 逻辑时间戳（当前未使用，留待 TTL） |
| id | long long int | 对象唯一标识 |
| size | uint32 | 对象大小（字节） |
| extra | uint16 (可选) | 分类特征，可多列，预留 |

示例:
```
0 1 45
0 2 510
0 3 35
1 2 510
1 4 233
```

## 模型

- `bit` (默认): cost = size（按字节计代价）
- `fault`: cost = 1（每次未命中代价相同）
- `general`: cost = size（预留扩展）


## 输出指标

| 指标 | 说明 |
|------|------|
| total_requests | 请求总数 |
| hits / misses | 命中 / 未命中次数 |
| OHR (hit_rate) | 对象命中率 = hits / total_requests |
| byte_total / byte_hit | 字节总流量 / 命中字节数 |
| BHR | 字节命中率 = byte_hit / byte_total |
| evictions | 驱逐次数（local_ratio_caching 的口径见下方"驱逐口径"说明） |
| competitive_ratio | 对象数竞争比 = online_misses / belady_misses（fault 模型代价比） |
| byte_competitive_ratio | 字节数竞争比 = online 字节代价 / belady 字节代价（bit 模型代价比） |
| fetch_cost | Bit-Model 取回代价（仅 bit_model_online，即其字节代价） |
| cost | Local-Ratio-Caching 总 reload 代价（仅 local_ratio_caching，即其优化的字节/未命中代价） |

> **两个竞争比**：均以 Belady 为基准。
> - **对象数竞争比** = 算法未命中次数 / Belady 未命中次数（fault 模型，每次未命中代价为 1）；
> - **字节数竞争比** = 算法字节代价 / Belady 字节代价（bit 模型，代价为取回字节数）。
>
> **关于 Belady **：Belady MIN（驱逐下次使用最远的项）在**等长页面**（经典分页）下是离线最优；但本框架是**变长对象缓存**，变长离线最优是 NP 难的，Belady 在此仅是**启发式基准**、并非真正最优。
>
> 字节代价取各算法的取回字节数：LRU/Belady 为字节未命中量 (byte_total − byte_hit)，bit_model_online 因维护缓存状态分布会额外取回页面，其字节代价取 fetch_cost
>
> **驱逐口径（LocalRatioCaching）**：其输出是“保留哪些实例”的可行调度，需等价转换为实际驱逐操作，两类驱逐均计数：(a) **真实实例未调度** -- 页面在上次请求后被驱逐、下次请求重载；(b) **虚拟实例（死页）未调度** -- 死页（含仅请求一次就不再请求的对象）按“下次请求为 n+1”建虚拟实例 [末次请求+1, n]，未调度意味着末次请求后驱逐，被调度则保留至 trace 结尾。故其驱逐数 = 未调度真实实例数 + 未调度虚拟实例数（虚拟实例的 penalty 仅存在于模型、不计入 cost）。因此驱逐数 ≥ Belady/LRU 的簿记驱逐数（后者不计死页滞留、也不立即清理）属正常现象；判断容量压力应看 miss 与竞争比，而非其驱逐数。

### LocalRatioCaching 递归过程记录（每轮最拥塞时间点 t* 与删除实例的对象大小范围）

local-ratio 算法（离线 4-近似）每轮递归先找**最拥塞时间点 t\***（argmax Δ(t)，Δ(t)=Σ覆盖 t 的存活实例宽度−Width(t)），再对覆盖 t\* 的实例集 Z(t\*) 按比例因子 p 削减 penalty 并删除降为 0 的实例；当 max Δ ≤ 0（全部实例共同可行）时终止。下表逐轮记录 t\*、Δ\*、|Z(t\*)|、删除实例数，以及**删除实例对应的对象大小范围 [min, max] 与总大小**（bit 模型 penalty=width=size，实测各轮 p=1）。

**死页建模对递归结构的影响**：请求一次就不再请求的死页按“下次请求为真实 n 次之后的第 n+1 次”建虚拟实例 [末次请求+1, n]，全部延伸到 trace 末端。三个真实 trace 的一次性死页占唯一对象的 78%–97%（占唯一字节的 79%–97%），故**第 1 轮 t\* 均落在 trace 末端**（twitter29 t\*=9564=n−2、twitter45 t\*=10000=n、wiki2018 t\*=9999=n−1），覆盖该点的存活实例恰为全部虚拟实例（|Z|=虚拟实例总数：twitter29 5715、twitter45 9319、wiki 6480/6497/6503——随容量增大，不可缓存的巨型页减少），一轮全部删除；其后各轮（真实拥塞轮）才处理真实实例的拥塞。

**观察**：

- **末端死页轮（死页扩展建模的直接体现）**：真实 trace 的第 1 轮 t\* 落在 trace 末端——一次性死页的虚拟实例全部延伸到末端、在末端堆积成最拥塞点，覆盖该点的存活实例几乎全为虚拟实例（twitter45 t\*=n 时严格全为虚拟 9319 个；twitter29 t\*=n−2 时 5713 虚拟 + 2 个下次请求恰在最后两条请求的真实实例；wiki t\*=n−1 时 6479 虚拟 + 1 个），p=1 下一轮全部删除（删除对象大小范围覆盖全谱：twitter29 [35, 49465]、twitter45 [1, 1014]、wiki 5% [89, 12542746] 含最大对象；twitter29 该轮删除总大小 3411509 字节 = 唯一对象总字节 3411929 − 420，其中 420 为末次请求恰在 t\*=9564 的死页——其虚拟实例区间 [9565, 9566] 不覆盖 t\*，未入本轮删除集）。其后各轮才处理真实实例的拥塞；经逐实例核验，其**删除集合与完全不为死页建虚拟实例时完全相同**（twitter29 1%：当前轮 2–7 ≡ 原算法轮 1–6，轮 8 = 原轮 7 减去被末端轮提前扫掉的那 1 个覆盖 t\* 的真实实例；各轮仅删除顺序不同，只影响阶段二贪心补回的次序）。
- **缓存越紧张、递归轮数越多**：1% 时总轮数 synthetic 11 / twitter29 8 / twitter45 4 / wiki 4；随缓存增大轮数减少，真实 trace ≥5% 后仅剩末端死页轮（共 1 轮，miss 全为 compulsory、竞争比 1.0000）；synthetic ≥2% 连死页轮也不触发（0 轮，全部实例含虚拟实例初始即共同可行）。
- **Δ\* 逐轮严格递减**：每轮删除 Z(t\*) 中 penalty 归零的实例后，最拥塞点的过载量快速收敛（twitter29 1%：3361258 → 166310 → 95512 → 52784 → 27939 → 14658 → 7228 → 3770 字节；synthetic 1%：275 → … → 3 字节）。
- **删除对象大小范围随 Δ\* 收窄（synthetic 1% 最明显）**：前 7 轮 Δ\* ≥ 204 ≥ 最大对象大小（74 字节），覆盖 t\* 的实例全谱删除（[1, 74]）；后 4 轮 Δ\* 降至 64/44/33/3 字节，penalty 削减只能归零宽度不超过 Δ\* 的小对象，删除范围上界相应降至 44/44/27/3——过载量越小，被“挤掉”的越只有小对象。
- **t\* 分布与 trace 局部性一致**：twitter29 真实拥塞轮的 t\*（4105、6936、1100、8376…）对应请求序列中重复访问密集的时间段；twitter45 时序局部性极弱（9031/9320 个对象仅请求一次），仅 1% 时有 3 轮真实拥塞且 Δ\* 很小（首个真实拥塞轮 10141 字节）。
- **wiki2018 的 Δ\* 显著大于其他 trace**：末端死页轮 Δ\* 达 2.2–3.5 亿字节（一次性死页占唯一字节的 97.3%，几乎全部堆积在 trace 末端）；真实拥塞轮 Δ\* 也达 0.4–4.6 MB（对象大小极度不均，最大 12.5MB）。
- **容量对同轮 Δ\* 的影响**：所有页面可缓存时（twitter29/45，最大对象 < 1% 容量），实例集合与容量无关、Width(t) 逐点恰减容量增量，故各轮 t\* 不变、Δ\* 恰减容量差（twitter29 1% vs 2%：末端轮 3361258−3310587=50671、首个真实拥塞轮 166310−115639=50671，均等于容量差）。wiki2018 有巨型页跨过容量阈值：1% 下 23 个 >3.8MB 的页（合计 1.43 亿字节）不可缓存、不参与实例构造，2% 下减为 6 个——实例集合本身随容量变化，故无上述平移关系（首个真实拥塞轮 t\* 1%=5084 vs 2%=4428，且 2% 的 Δ\* 反而更大：新增可缓存的大页实例加入拥塞）。这是论文假设 0<s(j)<S 之外扩展 `cacheable=s≤S` 的正确行为：不可缓存页为强制未命中、不参与优化。
- **死页建模对调度质量的影响（三版本对照）**：死页无未来请求，保留或驱逐它都增减不了任何 reload——故**完整建模（含一次性死页）相对完全不建模在真实目标上是中性的**（twitter29 1%：miss 6264→6240、cost 3783920→3784081，差异 ≤±0.05%，属阶段二贪心平局方差；末端轮连带扫掉的两个末端真实实例在两版本中最终调度命运相同）。关键对照是**部分建模**（仅多请求死页建虚拟实例）：其末端拥塞（725K）不足以压倒内部点，第 1 轮为混合轮（t\*=9302，1175 虚拟 + 54 真实一并删除），内部递归从此被扰动（第 2 轮 Δ\* 161497≠166310，各轮 |Z| 均偏离），cost 甚至高于完全不建模（twitter29 3784656>3783920、wiki2018 370335530>370121810）；完整建模使末端拥塞（3.36M）绝对占优，全部虚拟实例在一轮纯末端轮中隔离清场，内部删除集合与完全不建模逐实例相同，cost 回到无建模水平（3784081；wiki2018 的 370121559 还略优于无建模的 370121810）。synthetic 无一次性死页，结果不变。

### 结果分析

- **Belady** 作为离线基准，两个竞争比恒为 1.0000。需注意 Belady MIN 仅在等长页面下最优；本框架为变长对象缓存，离线最优是 NP 难的，故 Belady 在此是启发式基准，其命中率并非严格上界。
- **缓存大小的影响**：随缓存从 1% 增至 10%，各在线算法命中率提升、两个竞争比同步下降。
- **LRU** 表现均衡：真实 trace 上对象数竞争比约 1.03–1.27、字节数竞争比约 1.02–1.16，两者量级接近，说明 LRU 对“命中次数”与“字节代价”无偏向。
- **bit_model_online 以字节代价为优化目标**：其字节数竞争比在三个真实 trace 上为 **1.03–1.18**，接近 Belady 基准，符合 O(log k) 量级的理论竞争比保证；但对象数竞争比普遍偏高（1.04–1.40），OHR 多低于 LRU--这是用对象命中换取字节代价优化的预期折中。
- **wiki2018 上两竞争比分化最明显**：对象大小极度不均（最大 12.5MB，少数大对象主导字节流量），bit_model_online 对象数竞争比高达 1.30–1.40，而字节数竞争比仅 1.03–1.07--算法优先缓存大对象以压低字节取回代价，对小对象的未命中不敏感。
- **synthetic_test 上算法优势无法体现**：对象大小几乎全为 1 字节、缓存小（1%）且驱逐频繁时，bit_model_online 维护缓存状态分布的额外取回开销被放大，1% 时两竞争比分别达 3.41/3.10；当缓存 ≥ 2%（≥ 3235 字节，可容纳全部 1000 个对象的 1893 字节）后所有算法均无容量压力驱逐（LocalRatioCaching 驱逐数为 0——全部实例含死页虚拟实例初始即共同可行，死页保留至 trace 结尾），两竞争比均为 1.0000。
- **twitter45_test** 约 93% 请求为唯一对象、时序局部性极弱，各算法命中率整体偏低（OHR<0.07），属 trace 本身特性；此时两竞争比都接近 1（1.03–1.11），因几乎所有请求都是冷未命中，算法间差异有限。
- **LocalRatioCaching（离线 4-近似，优化字节代价）**：真实 trace 上字节数竞争比为 **0.9985–1.0014**、对象数竞争比 0.98–1.00，因为它直接优化 bit 模型的 reload 字节代价，而 Belady 仅是 fault 模型最优、并非 bit 模型最优；在变长 trace（twitter29 / wiki2018）小缓存下甚至 **优于 Belady**（如 wiki2018 2% 字节数竞争比 0.9985、对象数竞争比 0.9811，未命中数与字节代价均低于 Belady）。缓存足够大（≥5%）时它找到与 Belady 相同的最优调度（两竞争比均 1.0000、miss 全为 compulsory；其驱逐数为未调度虚拟实例数——即末次请求后被驱逐的死页数，而非容量压力所致）。仅在对象大小近均匀的 synthetic（1%）上劣于 Belady（1.07）--此时 fault≈bit 模型、Belady 近似最优。
- **LocalRatioCaching vs LRU（离线 vs 在线）**：两者一为离线 4-近似（可预知全部请求）、一为纯在线（无未来信息），对比直接体现离线优化的增益。在缓存紧张的真实 trace 上 LocalRatioCaching 全面压制 LRU：twitter29 1% 时 OHR 0.3477 vs 0.2622（+8.5pp）、对象数竞争比 0.9939 vs 1.1242；wiki2018 1% 时 OHR 0.3288 vs 0.1411（约 2.3 倍）、对象数竞争比 0.9925 vs 1.2700--LocalRatioCaching 甚至优于 Belady，而 LRU 明显劣于 Belady。两竞争比上 LocalRatioCaching 均贴近或低于 1、LRU 则稳定在 1.03–1.27，且差距随缓存增大而收窄。cache ≥5% 时 LocalRatioCaching 已找到无重载驱逐的最优调度（驱逐全部为未调度虚拟实例的死页清理，无容量压力重载），LRU 仍因时序贪婪频繁驱逐（如 twitter29 5% 驱逐 6271 次，全部因容量压力而非清理），OHR 落后约 30%。唯一无显著差异的是对象大小近均匀的 synthetic（≥2% 后两者均无重载、两竞争比同 1.0000）；但 1% 高压下 LocalRatioCaching 仍以 OHR 0.9798 vs 0.9543、竞争比 1.07 vs 2.42/2.48 明显占优。整体看，LocalRatioCaching 的优势源于「离线预知 + 字节代价优化」，代价是必须提前拿到完整 trace，无法用于在线场景。
- **离线视野的可分割性（见下方「分段实验」）**：并不需要完整 trace 才有优势——将序列均分为 k 段、段内独立求解后拼接，1% 容量下批次缩短到 n/20（约 500 条请求）时仍全面优于 LRU；但缓存充裕（≥5%）后分段解钉死在分段冷启动下界，反被持续改善的 LRU 反超。

### 分段实验（有界离线视野：分段 LocalRatioCaching vs 全局解）

实际系统往往拿不到完整 trace，只能按批次获得一段请求。本实验将整条请求序列均分为 k 段（k=10/20/50/100），**每段独立、从空缓存运行修改后的 LocalRatioCaching**（段内一次性死页同样按「下次请求为该段第 n_seg+1 次」建虚拟实例），各段局部解直接拼接为合并解，与整条 trace 的全局解比较，度量**离线视野缩短的代价**。

- **冷启动下界**：任何分段方案（无论段内算法好坏）的 miss ≥ Σ各段段内不同对象数、bit 代价 ≥ Σ各段段内不同对象字节和，用于区分「分段固有损失」（段边界 compulsory miss）与「段内算法损失」。三个 trace 的分段下界 miss（k=10/20/50/100）：twitter29 6767/7036/7415/7881、twitter45 9721/9804/9876/9924、wiki2018 8042/8492/8984/9300。
- 10% 容量下全局与分段结果均与 5% 完全相同（miss/cost 不再随容量变化），下表仅列 1%/2%/5%。
- 复现：`python run_segment_experiment.py [trace...]`（默认 twitter29_test10.csv，支持 `--pcts / --segments / --cost-model`）。

- **退化幅度由跨段复用度决定**：twitter45 跨段复用极少，miss 仅退化 2.8%–6.5%；twitter29 热门对象跨段复用多，退化 8.6%–37.9%；wiki2018 居中，退化 17.7%–43.0%。
- **分段伤「次数」不伤「字节」（wiki2018 最明显）**：miss 最多 +43.0%，cost 仅 +1.5%–4.1%——段边界补进来的全是跨段复用的热门小对象（wiki2018 5% k=10 相比全局额外 1538 次 miss 仅多 12.0MB、平均 7.8KB/次），占唯一字节 97.3% 的巨型一次性对象无论分段与否都只 compulsory 载入一次。对以字节代价为目标的 bit 模型，分段的实际代价出奇地小。
- **分段解钉死在冷启动下界、不随容量改善，故相对退化随容量增大**：容量 ≥2%（twitter45/wiki2018）或 ≥5%（twitter29）后各段内部无拥塞，分段 miss/cost 与容量无关（表中 2% 与 5% 的分段值相同）；而全局解随容量增大持续下降（twitter29 全局 miss 6240→5903→5716），1% 时比值反而被大分母（全局自身的容量压力重载）稀释。
- **与 LRU（纯在线）对比给出离线视野的实用界**：1% 容量下 k≤20（批次 ≈ n/20 ≈ 480–500 条请求）的分段解在 miss 与字节代价上仍全面优于 LRU（twitter29 k=20：miss 7038 vs 7058、cost 4165730 vs 4197898；twitter45 k=20：9804 vs 9867；wiki2018 k=20：8492 vs 8589、cost 377117957 vs 377384923）；2% 下 k=10 仍优；5%–10% 下分段解钉在下界、被持续改善的 LRU 反超（twitter29 10%：k=10 的 6767 vs LRU 6281；wiki2018 5%：8042 vs 7880）。结论：**缓存紧张时，离线视野缩短到 ~n/20 仍胜过在线算法；缓存充裕时，短视野离线反而不如零视野在线**。
- **「末端死页轮」按段复制**：中小容量（1%–5%）下 k=10 时总轮数 ≈ k——每段恰 1 轮，即该段自己的「末端死页轮」（实测 twitter29 2% 各段：t\*=956~957=段末、|Z|=663~700 为该段全部虚拟实例，一轮全删），与全局解的末端死页轮机制同构。容量更大或段更短后段内连死页轮也消失（twitter29 10% k=10 时 rounds=0；三个 trace 5%–10% 下 k≥50 时各段 rounds=0、evictions=0——段内全部实例含虚拟实例初始即共同可行，段的代价只剩边界冷启动）。

## 扩展新算法

实现 `EvictionPolicy` 子类并用 `@register("name")` 注册:

```python
from cache_sim.core.policy import EvictionPolicy
from cache_sim.algorithms.registry import register

@register("my_algo")
class MyAlgorithm(EvictionPolicy):
    def __init__(self):
        super().__init__("MyAlgo")
        self._data = {}

    def on_hit(self, key, ctx):
        self._data[key] = ctx.time

    def on_admit(self, key, ctx):
        self._data[key] = ctx.time

    def on_evict(self, key):
        self._data.pop(key, None)

    def select_victim(self, candidates, ctx):
        return min(candidates, key=lambda k: self._data.get(k, 0))

    def reset(self):
        self._data.clear()
```

然后在 `cache_sim/algorithms/__init__.py` 中添加导入:

```python
import cache_sim.algorithms.my_algo  # noqa: F401
```
